## 1. (Spec Q10) delayed_sip WebSocket wildcard and symbol counting; REST bars for many symbols with end <= now-15min

### Takeaway
Whether `bars:["*"]` is accepted on `v2/delayed_sip` (or `v2/iex`) on the Basic plan, and how the 30-symbol Basic limit is counted (per symbol, per channel-symbol pair, wildcard), is NOT documented; it needs a raw-WebSocket paper-key test. The REST fallback is documented well enough to implement: `GET /v2/stocks/bars` with comma-separated `symbols`, `feed=sip` (the historical `feed` enum does NOT list `delayed_sip`), `end` at least 15 minutes old, `limit` up to 10000 data points per page across all symbols, results sorted symbol-first, paginated with `next_page_token`; no maximum symbol count is documented (one staff post says about 3000, bounded by URL length).

[H] — [About Market Data API, updatedAt 2026-10-06](https://docs.alpaca.markets/us/docs/about-market-data-api.md)

REST side (SIP bars at least 15 minutes old)
- Endpoint `GET /v2/stocks/bars` ("Historical bars"): "provides aggregates for a list of stock symbols between the specified dates. The returned results are sorted by symbol first, then by bar timestamp. This means that you are likely to see only one symbol in your first response if there are enough bars for that symbol to hit the limit you requested. In these situations, if you keep requesting again with the `next_page_token` from the previous response, you will eventually reach the other symbols if any bars were found for them." [H] — [Historical bars reference, updatedAt 2026-05-27](https://docs.alpaca.markets/us/reference/stockbars.md)
- Parameters (OpenAPI in the same page): `symbols` "A comma-separated list of stock symbols." (required); `timeframe` (`[1-59]Min`/`T`, `[1-23]Hour`/`H`, `1Day`, `1Week`, months); `start`/`end` RFC-3339 or YYYY-MM-DD, "inclusive"; `limit` default 1000, minimum 1, maximum 10000, and "The limit applies to the total number of data points, not per symbol!"; `adjustment` (default raw); `asof`; `feed`; `currency`; `page_token`; `sort`. [H] — [Historical bars reference](https://docs.alpaca.markets/us/reference/stockbars.md)
- `start` default: "the beginning of the current day, but at least 15 minutes ago if the user doesn't have real-time access for the feed." `end` default: "the current time if the user has a real-time access for the feed, otherwise 15 minutes before the current time." [H] — same page
- Historical `feed` enum in the REST reference: `iex`, `otc`, `sip`, `boats` (schema default "sip"). `delayed_sip` is NOT in this enum; it IS in the enum of the "latest" and "snapshots" endpoints ("`delayed_sip`: SIP with a 15 minute delay"; "Default: `sip` if the user has the unlimited subscription, otherwise `iex`"). [H] — [bars](https://docs.alpaca.markets/us/reference/stockbars.md), [latest quotes](https://docs.alpaca.markets/us/reference/stocklatestquotes-1.md), [snapshots](https://docs.alpaca.markets/us/reference/stocksnapshots-1.md) (all updatedAt 2026-05-27)
- CONTRADICTION (client vs docs): alpaca-py `StockBarsRequest.feed: Optional[DataFeed]` accepts `DataFeed.DELAYED_SIP`, so the SDK will happily send `feed=delayed_sip` to `/v2/stocks/bars`, which the REST reference does not list. [H] — [alpaca/data/requests.py L85-L106](https://github.com/alpacahq/alpaca-py/blob/dc5f6f53963b9e0e9e62bc35c9041a122aa95cdc/alpaca/data/requests.py#L85-L106)
- Rule for Basic: "All the latest endpoints (including the snapshot endpoint), require a subscription to be used with the SIP feed. For historical queries, the `end` parameter must be at least 15 minutes old to query SIP data without a subscription. The default value for `feed` is always the "best" available feed based on the user's subscription." Error when violated (FAQ sample): `{"code":42210000,"message":"subscription does not permit querying recent SIP data"}`. [H] — [Market Data FAQ, updatedAt 2026-09-21](https://docs.alpaca.markets/us/docs/market-data-faq.md)
- CONTRADICTION (error code/status): Alpaca's learn article shows the same message as `{'response_status_code': 403, ... {"code":40010001,"message": "subscription does not permit querying recent SIP data"}}`, whereas the FAQ shows code `42210000`. Do not key logic on the numeric code; key on the message text or HTTP 403/422. [M] — [Alpaca Trading API Error Cheat Sheet, 2026-03-04](https://alpaca.markets/learn/how-to-fix-common-trading-api-errors-at-alpaca)
- Real behaviour confirmed by staff (2026-06-16, in a thread where a paper bot requested `feed=sip` with no `end`): "The end parameter defaults to the most recent time for which data can be accessed with the user's market data subscription. This is the current time if one has an Algo Trader Plus market data subscription, and 15 minutes before the current time if not." Also: with `limit` and no `start`/`end`/`sort`, the API returns the first bars of the day ascending, and the limit is total bars, not per symbol; "bars are only created if there are valid trades during the bar". [M] — [forum topic 19126](https://forum.alpaca.markets/t/19126), post #2
- Symbols per call: no maximum is stated in the reference. Staff (2023-01-19): "Most, if not all the data calls provide for multiple symbols. It's a 'best practice' to, for example, make a single call of 100 symbols rather than 100 calls for one symbol each." and "the max number of symbols in a single call is about 3000. There isn't a fixed limit but the symbols become part of the API URL. With 3-4 characters per symbol, the URL gets to be very long. Some networks don't handle very long URLs and may give an error. I personally try to stay under 3000 symbols per call." [M, dated 2023] — [forum topic 11614](https://forum.alpaca.markets/t/11614), posts #2 and #4
- Rate budget: each page request is one call against the Basic data limit of 200/min (see section 4). alpaca-py `get_stock_bars` auto-paginates (`page_size=10_000`, loops on `next_page_token`) and each page is a separate HTTP call. [H] — [alpaca/data/historical/stock.py L75-L96](https://github.com/alpacahq/alpaca-py/blob/dc5f6f53963b9e0e9e62bc35c9041a122aa95cdc/alpaca/data/historical/stock.py#L75-L96), [alpaca/common/rest.py L371-L411](https://github.com/alpacahq/alpaca-py/blob/dc5f6f53963b9e0e9e62bc35c9041a122aa95cdc/alpaca/common/rest.py#L371-L411)

### Inferences
- A request of the form `GET https://data.alpaca.markets/v2/stocks/bars?symbols=A,B,...&timeframe=1Min&start=<RFC3339>&end=<now-16min RFC3339>&feed=sip&adjustment=raw&limit=10000&sort=asc` (then follow `next_page_token`) is consistent with every documented rule and needs no subscription. Using `end` slightly older than 15 minutes (for example 16) is a safety margin against clock skew; this is my suggestion, not a documented requirement. [M]
- Sizing: 5 one-minute bars (09:30-09:35) per symbol means roughly 5 x N data points; at 10000 per page that is about 2000 symbols per page when every symbol has all five bars, fewer pages because illiquid symbols have missing bars (bars exist only if trades occurred). Because results are ordered symbol-first, a page boundary can fall inside one symbol's bars, so a client must merge across pages. [M, arithmetic from documented limits]
- The doc statement "Basic: SIP only older than 15 minutes" plus the staff 2026-02-05 statement make `v2/delayed_sip` very likely usable on Basic, but "very likely" is not a test; the wildcard and the counting rule remain open. [L]

### Gaps
- Does `{"action":"subscribe","bars":["*"]}` succeed on `v2/delayed_sip` and on `v2/iex` with a Basic (paper-only) key? Not documented. Needs: one raw WebSocket session (not alpaca-py, which only logs errors) to `wss://stream.data.alpaca.markets/v2/delayed_sip`, authenticate with paper keys, send that single subscribe message, record the reply (a `subscription` ack with `"bars":["*"]`, or an error 405/409/410). Repeat on `v2/iex`.
- How symbols are counted vs 30: not documented. Needs the same session: subscribe `trades:["AAPL"]`, then `quotes:["AAPL"]`, then `bars:["AAPL"]` and compare the count at which 405 appears when adding distinct symbols (30 vs 31), and whether a prior `bars:["*"]` consumes the allowance.
- Whether `/v2/stocks/bars?feed=delayed_sip` is accepted: not documented (absent from the enum, present in the SDK enum). One REST call settles it; otherwise use `feed=sip` with an old `end`.
- Documented maximum of symbols per bars request: absent; only the 2023 staff estimate (about 3000, URL-length bound).

## 2. (Spec Q11, Q17, Q18) OTO and bracket on whole shares: parameters, partial fills, leg exposure, sibling and race behaviour

### Takeaway
An OTO with only a `stop_loss` is explicitly allowed (docs and alpaca-py validator). The exit leg is NOT active until the entry is COMPLETELY filled, so partially filled shares are unprotected (Alpaca staff confirmed this on 2026-07-30); the docs do not say what happens to the held stop when an entry never completes. Legs are visible only via `nested=true` (REST) or the POST response; trade_updates do not populate `legs` and instead carry `group_id`/`group_role` on the order; legs have their own `id` and an auto-generated `client_order_id` that differs from the parent's and cannot be set in the request. The docs contradict themselves on whether OTO (and bracket) legs can be replaced.

### Cited Findings
Required parameters and restrictions
- OTO: "OTO (One-Triggers-Other) is a variant of bracket order. It takes one of the take-profit or stop-loss order in addition to the entry order. For example, if you want to set only a stop-loss order attached to the position, without a take-profit, you may want to consider OTO orders." and "Either of `take_profit` or `stop_loss` must be present (the above example is for take-profit case), and the rest of requirements are the same as the bracket orders." (The JSON example under it actually carries a `stop_loss`; the parenthetical is a doc typo.) [H] — [Placing Orders, updatedAt 2026-08-10](https://docs.alpaca.markets/us/docs/orders-at-alpaca.md)
- Bracket requirements (OTO inherits "the rest"): "`order_class` as "bracket"", `take_profit` object with `limit_price`, `stop_loss` object with mandatory `stop_price` and optional `limit_price` ("If `limit_price` is specified in `stop_loss`, the stop-loss order is queued as a stop-limit order, but otherwise it is queued as a stop order"); "Both `take_profit.limit_price` and `stop_loss.stop_price` must be present." (bracket); "Extended hours are not supported. `extended_hours` must be "false" or omitted."; "`time_in_force` must be `day` or `gtc`."; "Each order in the group is always sent with a DNR/DNC (Do Not Reduce/Do Not Cancel) instruction". [H] — same page
- Stop-price threshold: "The stop price input has to be at least $0.01 below (for stop-loss sell, above for buy) than the "base price"." Base price = entry limit price if the entry is a limit order, and "also the current market price for any, of OCO, OTO and bracket." "This restriction is to avoid potential race-conditions in the order handling, but as we improve our system capability, this may be loosened in the future." The exact error text for a violation is not documented ("the order request can be rejected"). [H] — same page
- Whole-quantity orders: market, limit, stop, stop-limit all accept `DAY` and `GTC` in the "Whole qty orders (USD)" table. [H] — same page
- Request schema for the nested objects: `stop_loss`: "Takes in string/number values for stop_price and limit_price"; `take_profit`: "Takes in a string/number value for limit_price"; `limit_price` required "if type is `limit` or `stop_limit`". The nested objects have no `client_order_id`, `qty` or `time_in_force` field. [H] — [Create an Order reference, updatedAt 2026-05-27](https://docs.alpaca.markets/us/reference/postorder.md)
- alpaca-py validation: bracket and OCO "require take_profit.limit_price" and "stop_loss.stop_price"; OTO "require[s] either take_profit or stop_loss" (so stop-only OTO is accepted client-side); `LimitOrderRequest` requires `limit_price` unless OCO; `TakeProfitRequest.limit_price: float`, `StopLossRequest.stop_price: float`, `limit_price: Optional[float]`; no client-side TIF/extended-hours/leg-id checks. All prices are `float`. [H] — [alpaca/trading/requests.py L151-L173, L262-L287, L352-L400, L534-L578](https://github.com/alpacahq/alpaca-py/blob/dc5f6f53963b9e0e9e62bc35c9041a122aa95cdc/alpaca/trading/requests.py#L151-L173)
- Docs own Python example of an OTO with stop-only: `LimitOrderRequest(symbol="SPY", qty=5, limit_price=350, side=BUY, time_in_force=DAY, order_class=OrderClass.OTO, stop_loss=StopLossRequest(stop_price=300))`. [H] — [Working with /orders, updatedAt 2026-08-18](https://docs.alpaca.markets/us/docs/working-with-orders.md)

Partial fill behaviour and child quantity
- "The second and third orders won't be active until the first order is completely filled." (bracket section). [H] — [Placing Orders](https://docs.alpaca.markets/us/docs/orders-at-alpaca.md)
- Staff, 2026-07-30, on exactly the engine's case (BUY limit DAY entry, OTO, stop-only child, partial fill): "No. If the BUY entry order is still open, it implies that the associated stop-loss order is also still open. Submitting a second stop-loss order would effectively try to sell the same shares twice, since you already have an open order to sell them." and "Since you are submitting an OTO order, the stop loss order will not be submitted and therefore not active until the initial by entry order fills complete. Any partially filled shares will be, as you stated "unprotected" until the initial by order fills complete and the stop loss order is submitted." and "The paper and live trading environments are identical in how OTO orders are processed. ... Partial fills are rare in live trading. However, partial fills are intentionally exaggerated a bit in paper trading". [H/M: official staff, single post] — [forum topic 19417](https://forum.alpaca.markets/t/19417), post #2
- Consistent with the wash-trade table in the docs: an existing "market buy" followed by a new "stop sell" is "always rejected" (HTTP 403); "bracket or OCO ... and trailing stop orders are exceptions". OTO is not named in that sentence. [H] — [User Protection, updatedAt 2026-09-16](https://docs.alpaca.markets/us/docs/user-protection.md)
- Staff, 2020-12-22 (older): after the parent "completely fills (ie not a partial fill) the typical state would be the take profit limit order leg is set to new and the stop loss leg remains held." So a stop leg with status `held` after the entry fill is normal; it is the broker-side held stop (stops "are elected on the consolidated print" per the order-handling section of the orders page). [M, 2020] — [forum topic 3697](https://forum.alpaca.markets/t/3697), post #2
- Child quantity: the docs' bracket example response shows parent `qty "10"` and both legs `qty "10"`, status `held`. For the leg quantity during a partial fill of the entry there is no documented rule beyond "not active until completely filled". The only documented resize rule is for the take-profit leg: "If the take-profit order is partially filled, the stop-loss order will be adjusted to the remaining quantity." [M for the example, H for the quoted rule] — [Create an Order reference](https://docs.alpaca.markets/us/reference/postorder.md), [Placing Orders](https://docs.alpaca.markets/us/docs/orders-at-alpaca.md)
- Paper partial fills: "When orders are eligible to be filled, they will receive partial fills for a random size 10% of the time. If the order price is still marketable, the remaining quantity would be re-evaluated for a subsequent fill." [H] — [Paper Trading, updatedAt 2026-07-07](https://docs.alpaca.markets/us/docs/paper-trading.md)

How legs are exposed
- "Each order of the group is reported as an independent order in GET /v2/orders endpoint. But if you specify additional parameter nested=true, the order response will nest the result to include child orders under the parent order with an array field legs in the order entity." `nested` exists on `GET /v2/orders` and `GET /v2/orders/{order_id}` ("If true, the result will roll up multi-leg orders under the legs field of primary order."); `GET /v2/orders:by_client_order_id` documents only the `client_order_id` query parameter (no `nested`). [H] — [Placing Orders](https://docs.alpaca.markets/us/docs/orders-at-alpaca.md), [Get All Orders](https://docs.alpaca.markets/us/reference/getallorders-1.md), [Get Order by ID](https://docs.alpaca.markets/us/reference/getorderbyorderid-1.md), [Get Order by Client Order ID](https://docs.alpaca.markets/us/reference/getorderbyclientorderid.md)
- The POST response example for a bracket shows `legs` populated with two leg orders, each with its own `id`, its own `client_order_id` (different from the parent's: parent `5c2e8f1a-...`, take-profit leg `2d7e9b41-...`, stop-loss leg `8a4c1f6e-...`), `legs: null`, `status: "held"`, `order_class: "bracket"`, `position_intent: "sell_to_close"`, and shared `group_id` with `group_role` `entry`/`take_profit`/`stop_loss`. [M: one documented example; description reads "A `bracket` order returned with its legs. The entry order and both legs share one `group_id`, and `group_role` identifies each order."] — [Create an Order reference](https://docs.alpaca.markets/us/reference/postorder.md)
- `group_id`: "Opaque identifier shared by every order in the same `bracket`, `oto`, or `oco` order, including its legs and any replacement orders. Use it to associate related orders received from the `trade_updates` stream, where `legs` is not populated. Omitted for other orders." `group_role`: `entry`, `take_profit`, `stop_loss` ("The entry order of a `bracket` or `oto` order"). Leg `legs`: "Always null for an order leg; legs are not nested beyond one level." [H] — [Create an Order reference](https://docs.alpaca.markets/us/reference/postorder.md)
- alpaca-py: `Order.legs: Optional[List[Order]]`, `Order.group_id: Optional[UUID]`, `Order.group_role: Optional[Union[OrderGroupRole, str]]`, `OrderStatus.HELD = "held"`, `OrderGroupRole` enum (entry/take_profit/stop_loss); `GetOrdersRequest.nested`, `GetOrderByIdRequest.nested`. The group fields were added in commit `9233658` (2026-10-15, "fix(trading): parse order group_id and group_role (#815)"), so an alpaca-py older than that silently drops `group_id` (pydantic default ignores unknown fields). [H] — [alpaca/trading/models.py L217-L306](https://github.com/alpacahq/alpaca-py/blob/dc5f6f53963b9e0e9e62bc35c9041a122aa95cdc/alpaca/trading/models.py#L217-L306), [alpaca/trading/enums.py L160-L169, L214-L243](https://github.com/alpacahq/alpaca-py/blob/dc5f6f53963b9e0e9e62bc35c9041a122aa95cdc/alpaca/trading/enums.py#L160-L169)
- Whether `client_order_id` is inherited: the documented example says no (distinct values); the request schema offers no way to set a leg id. Nothing in prose states the rule. [M]

Sibling, replace, cancel, races
- Sibling on fill (bracket): "Once one of the exit orders is filled, the other is canceled. Please note, however, that in extremely volatile and fast market conditions, both orders may fill before the cancellation occurs." (the only documented double-fill warning). An OTO with one leg has no sibling. [H] — [Placing Orders](https://docs.alpaca.markets/us/docs/orders-at-alpaca.md)
- Group cancel: "If any one of the orders is canceled, any remaining open order in the group is canceled." [H] — same page
- Replace, CONTRADICTION inside one page: bracket bullet says "Order replacement (`PATCH /v2/orders`) is supported to update `limit_price` and `stop_price`." and OCO says "Like bracket orders, order replacement is supported to update limit_price and stop_price." but the OTO paragraph says "Like bracket orders, order replacement is not supported yet." [H that both sentences exist] — [Placing Orders, updatedAt 2026-08-10](https://docs.alpaca.markets/us/docs/orders-at-alpaca.md)
- PATCH reference: replace returns "The new Order object with the new order ID"; "A success return code from a replaced order does NOT guarantee the existing open order has been replaced. If the existing open order is filled before the replacing (new) order reaches the execution venue, the replacing (new) order is rejected, and these events are sent in the trade_updates stream channel."; "Order cannot be replaced when the status is `accepted`, `pending_new`, `pending_cancel` or `pending_replace`."; `client_order_id` on the patch body is "A unique identifier for the new order. Automatically generated if not sent. (<= 128 characters)"; "You can only patch full shares for now." The page says nothing about legs or `held` status. [H] — [Replace Order by ID, updatedAt 2026-05-27](https://docs.alpaca.markets/us/reference/patchorderbyorderid-1.md)
- Cancel: "Attempts to cancel an Open Order. If the order is no longer cancelable, the request will be rejected with status 422; otherwise accepted with return status 204." Lifecycle: `pending_replace` "will reject cancel request while in this state"; "An order may be canceled through the API up until the point it reaches a state of either `filled`, `canceled`, or `expired`." [H] — [Delete Order by ID](https://docs.alpaca.markets/us/reference/deleteorderbyorderid-1.md), [Placing Orders](https://docs.alpaca.markets/us/docs/orders-at-alpaca.md)
- Reserved shares and the cancel-then-close race (Alpaca's own troubleshooting article, 2026-03-04): sell/stop legs reserve the position ("These child orders reserve the position quantity until they are canceled or filled."); sending `DELETE /v2/orders` then immediately `DELETE /v2/positions/{symbol}` "If the second request hits the system before the cancellations are fully processed, the shares may still be considered reserved ... The close request then fails with an insufficient quantity error. In this case, wait for confirmation that the open orders are actually canceled before sending the close request." Error is HTTP 403 "insufficient qty available for order". [M, blog-grade official] — [Trading API Error Cheat Sheet, item 26](https://alpaca.markets/learn/how-to-fix-common-trading-api-errors-at-alpaca)
- PDT can block an exit leg in paper below $25,000 equity: staff walkthrough (2021-06-09) of a bracket whose take-profit never filled: "The order was blocked because of Pattern Day Trading (PDT) protection. Unless one has over $25,000 in their account, the PDT protections will prevent orders from being submitted which could result in going over the 3 day trades in 5 days rule." [M, 2021] — [forum topic 3697](https://forum.alpaca.markets/t/3697), post #9

### Inferences
- Engine impact (documented facts, my reading): with an OTO the shares filled so far are unprotected until the entry is fully filled; a stop cannot be added separately while the entry is open (403 wash-trade rule and staff Q1 answer). The engine therefore needs its own bounded "entry incomplete" handling (for example cancel the remainder and market-flatten or submit a standalone stop after the entry is canceled), and must not assume the broker stop exists while status is `partially_filled`. [M]
- Group-cancel rule plus "not active until completely filled" suggests that cancelling an unfinished entry could cancel the held stop and leave a partial position naked; the docs do not state this. [L]
- Replacing a stop leg to move the stop is documented as supported for bracket/OCO and "not supported yet" for OTO on the same page; do not design a trailing-by-replace flow on OTO without the test below. [M]
- Because `legs` is not in trade_updates and `get_order_by_client_id` has no `nested` option, the safe join key from stream events to the parent is `order.group_id` (and `order.group_role`), with `GET /v2/orders/{id}?nested=true` for the REST view. [M]

### Gaps
- Child stop quantity when the entry is only partially filled and then never completes (limit DAY expires, or the engine cancels the remainder): not documented. Paper test (spec Q17): submit a series of 1-3 marketable-limit OTO entries of ~20 shares with a stop_loss (paper gives random partial fills 10% of eligible fills); on each `partial_fill` event GET `/v2/orders/{id}?nested=true` and record leg `status`/`qty`; for one partially filled entry send `DELETE /v2/orders/{entry_id}` and record the leg status, the position qty, and whether any stop order exists.
- OTO leg replace/cancel while parent works (spec Q11): not documented beyond the contradiction above. Paper test, one order: OTO buy 1 share with `stop_loss`; (a) PATCH the stop leg `stop_price` while status `held` before fill (use a non-marketable limit entry); (b) after fill PATCH again; (c) DELETE the leg and observe whether the parent cancels. Record HTTP codes/messages.
- `client_order_id` inheritance (spec Q18): confirm with the first test order that `legs[*].client_order_id` differ from the parent and that `GET /v2/orders:by_client_order_id?client_order_id=<leg id>` returns the leg; confirm the stream's leg events carry `group_id` and `group_role`.
- Exact rejection text for a stop price within $0.01 of the base price: not documented (single paper order with `stop_price` = entry limit price settles it).

## 3. (Spec Q12) client_order_id: scope, lifetime, length, characters, duplicate error, lookup

### Takeaway
Uniqueness lifetime is NOT formally documented; Alpaca's own error guide words it as "another active order", which hints at open-order scope but does not promise reuse after fill/cancel. Maximum length is 128 characters; allowed characters are not documented. A duplicate returns HTTP 422 with `{"code":40010001,"message":"client_order_id must be unique"}` (per Alpaca's Mar-2026 error guide). Lookup is `GET /v2/orders:by_client_order_id?client_order_id=...`, in alpaca-py `TradingClient.get_order_by_client_id(client_id)`.

### Cited Findings
- "Each order has a unique identifier provided by the client. If the client does not provide one, the system will automatically generate a client-side unique order ID. ... Once an order is placed, it can be queried using either the client-provided order ID or the system-assigned unique ID to check its status." No scope (per account/forever) is stated. [H] — [Placing Orders, updatedAt 2026-08-10](https://docs.alpaca.markets/us/docs/orders-at-alpaca.md)

No pattern/charset is defined in the schema. Doc examples use UUIDs, `my_first_order`, `my_unique_id_123`. [H] — [Create an Order reference, updatedAt 2026-05-27](https://docs.alpaca.markets/us/reference/postorder.md), [Working with /orders](https://docs.alpaca.markets/us/docs/working-with-orders.md)
- Duplicate error, Alpaca's learn article "Alpaca's Trading API Error Cheat Sheet: 30 Common Errors Explained and Troubleshooting" (dated Mar 4, 2026), item 11 "Client_order_id must be unique (HTTP 422 Error)": "If you receive an HTTP 422 error like the one below, it likely means a duplicate client_order_id was used for another active order." sample `{'response_status_code': 422, 'response_text': {"code":40010001,"message":"client_order_id must be unique"}}` and "Make sure to use a unique client_order_id for each active order." - Lookup endpoint: `GET /v2/orders:by_client_order_id`, query parameter `client_order_id` (required, string), 200 "Successfully retrieved the order matching the client_order_id." ### Inferences
- Reading "for each active order" literally, reuse after the order is closed may be accepted, but this is an unverified reading of one "likely" sentence; the engine's own plan (a unique-by-construction id scheme) is the right default and makes the point moot. [L]
- Because alpaca-py retries a 504 on `POST /v2/orders` up to 3 times, a retry after an order that was actually accepted should come back 422 "client_order_id must be unique"; the engine should treat that exact 422 as "fetch by client_order_id and adopt" rather than as an error. [M, combination of documented retry code and documented duplicate response]
- Keep ids ASCII `[A-Za-z0-9_-]` and well under 128 characters (UUID-style); this is conservative practice, not a documented rule. [L]

### Gaps
- Scope after cancel/fill, and whether the lookup returns the older or newer order when reused: not documented. Paper test (spec Q12): (1) submit a non-marketable limit with `client_order_id=X`, cancel it, submit again with `X` and record status/body; (2) submit a 1-share marketable order with `X2`, let it fill, submit again with `X2`; (3) submit a 129-character id and an id containing `:` and a space and record the 422/403 text. Calls are single POSTs.
- Allowed character set: not documented anywhere found (a 2023 user report of a 422 for the numeric id "35899" on an IOC limit order, [topic 12223](https://forum.alpaca.markets/t/12223), is unanswered and probably unrelated). [L]
- HTTP code and body of `GET /v2/orders:by_client_order_id` for a missing id: not documented.

## 4. (Spec Q6) Trading API rate limit, headers, 429, trade_updates connection limit

### Takeaway
Trading API limit: 200 requests per minute per account, independent of any market-data subscription; this is documented only on an old support FAQ (Dec 2022) and by repeated staff forum answers (2024-2025), not on any current docs page I found (the docs index `llms.txt` lists a rate-limit page only for the Broker API, and the 17+ docs/reference pages I read give limits only for Market Data and Broker API). 429 body is `{"code":42910000,"message":"rate limit exceeded"}` and responses carry `X-RateLimit-Limit/Remaining/Reset`. Maximum concurrent trade_updates connections and the error returned for exceeding it are NOT documented; the 406 "connection limit exceeded" rule is documented for the market-data streams only.

## 5. (Spec Q4) SEC, TAF and CAT pass-through fees: aggregation, rounding, TAF waiver

### Takeaway

### Inferences
- Illustration of the difference (my arithmetic on the documented rates): a 100-share round trip has CAT = 100 x $0.000003 = $0.0003 per fill. Under daily per-account aggregation, all fills in the day sum per fee type and the total is rounded up once, to at least $0.01 per fee type per day. Under per-trade rounding each fill would cost $0.01. SEC fee on a $5,000 sell = $5,000 x 0.0000206 = $0.103, rounded up to $0.11 once per day per account (aggregated) or per sell (per trade). For a many-fills-per-day engine the choice changes the cost model materially, so use the PDF reading (daily, per-account, per fee type) as the base case and the per-trade reading as the pessimistic sensitivity. [M]
- Treat TAF as 0 only as of the 2026-10-12 schedule, with a stress case at FINRA's published $0.000195/share (max $9.79 per trade); the schedule is "subject to change without notice". [M]

### Gaps
- Whether the daily-aggregation statement or the older per-trade statement is operative; whether the TAF zero is a waiver, an absorption, or an error, and until when. Not answerable from public documents. Resolution path: the spec's planned support e-mail (spec Q4), asking exactly: (1) "Is each of SEC, TAF, CAT aggregated per day per account and rounded up once, or rounded per execution?" (2) "The fee schedule revised 2026-10-12 lists TAF as $0; is it waived, and until when?" ## 7. trade_updates: event types, reconciliation fields, and alpaca-py's TradeUpdate model

### Takeaway
The documented stream has 17 event types (7 "common", 10 "less common"); fields relevant for reconciliation are `event`, `order` (full REST-style object), `timestamp`, and for fills `price`, `qty`, `position_qty`, plus `execution_id` (shown in the example, not described in prose). alpaca-py's `TradeUpdate` exposes all of them but its `TradeEvent` enum lacks six documented events (they pass as plain strings), types the numeric fields as `float`, and makes `timestamp` required.

### Cited Findings
Docs (page updatedAt 2025-09-24; the page predates `group_id` and does not mention it)
- "The fields present in a message sent over the `trade_updates` stream depend on the type of event they are communicating. All messages contain an `event` type and an `order` field, which is the same as the order object that is returned from the REST API."
- Common events: `new` ("routed to exchanges for execution"); `fill` ("completely filled") with `timestamp`, `price`, `qty`, `position_qty`; `partial_fill` with `timestamp`, `price`, `qty`, `position_qty`; `canceled` (+`timestamp`); `expired` (+`timestamp`); `done_for_day`; `replaced` (+`timestamp`).
- Less common events: `accepted`, `rejected` (+`timestamp`), `pending_new`, `stopped`, `pending_cancel`, `pending_replace`, `calculated`, `suspended`, `order_replace_rejected`, `order_cancel_rejected`.
- Field definitions: `price` "The price per share for the fill event. This may be different from the average fill price for the order if there were partial fills."; `qty` "The number of shares for the fill event. This will be different from the filled quantity for the order if there were partial fills."; `position_qty` "The total size of your position after this event, in shares. Positive for long positions, negative for short positions."; `timestamp` "The time at which the order was filled / partially filled / canceled / expired / replaced / rejected".
- Example payload (a `fill`): keys `stream`, `data.event`, `data.execution_id` ("2f63ea93-423d-4169-b3f6-3fdafc10c418"), `data.order{...,"filled_qty","filled_avg_price","legs":null,...}`, `data.position_qty`, `data.price`, `data.qty`, `data.timestamp`. `execution_id` is not explained in the prose and the page makes no uniqueness/ordering/replay promise. The multileg-options example adds `event_id` (ULID), `at`, `position_qtys`, and `legs[]` each with `execution_id`, `qty`, `price`, `order_id`, `symbol`, `timestamp`; these are shown only for mleg.
- "Subscribing to real-time trade updates ensures that a user always has the most up-to-date picture of their account activity." Orders page: "Updates on open orders are also delivered through the streaming interface, which is the recommended method for maintaining order state."
- Paper stream uses binary frames; protocol: send `{"action":"listen","data":{"streams":["trade_updates"]}}`, server acks on stream `listening`; unauthorized variants as in section 4.
[H] — [Websocket Streaming](https://docs.alpaca.markets/us/docs/websocket-streaming.md); [Placing Orders](https://docs.alpaca.markets/us/docs/orders-at-alpaca.md)
- Order-level `group_id` is available on the nested order in the stream (OpenAPI text: "Use it to associate related orders received from the `trade_updates` stream, where `legs` is not populated"). [H] — [Create an Order reference](https://docs.alpaca.markets/us/reference/postorder.md)

alpaca-py (commit dc5f6f53963b9e0e9e62bc35c9041a122aa95cdc)
- Model definition, verbatim ([alpaca/trading/models.py L769-L782](https://github.com/alpacahq/alpaca-py/blob/dc5f6f53963b9e0e9e62bc35c9041a122aa95cdc/alpaca/trading/models.py#L769-L782)):
```python
class TradeUpdate(BaseModel):
    """
    Represents a trade update.

    ref. https://docs.alpaca.markets/docs/websocket-streaming#example
    """

    event: Union[TradeEvent, str]
    execution_id: Optional[UUID] = None
    order: Order
    timestamp: datetime
    position_qty: Optional[float] = None
    price: Optional[float] = None
    qty: Optional[float] = None
```
- Event enum, verbatim ([alpaca/trading/enums.py L464-L476](https://github.com/alpacahq/alpaca-py/blob/dc5f6f53963b9e0e9e62bc35c9041a122aa95cdc/alpaca/trading/enums.py#L464-L476)): `ACCEPTED, CANCELED, EXPIRED, FILL, NEW, PARTIAL_FILL, PENDING_CANCEL, PENDING_NEW, PENDING_REPLACE, REJECTED, REPLACED, RESTATED` (12 values). Documented events missing from the enum: `done_for_day`, `stopped`, `calculated`, `suspended`, `order_replace_rejected`, `order_cancel_rejected`. `restated` is in the enum but not on the docs page. Because `event` is `Union[TradeEvent, str]`, the missing ones arrive as plain `str`; known ones arrive as `TradeEvent` (a `str` subclass, so `== "fill"` works). [H]
- `TradeUpdate` is a plain pydantic `BaseModel` (default `extra="ignore"`), so unknown keys such as `event_id`, `at`, `position_qtys`, mleg `legs` are dropped; `price`/`qty`/`position_qty` are converted to Python `float` (the Order sub-model keeps `qty`/`filled_qty`/`filled_avg_price` as `Union[str, float]`). [H]
- `timestamp: datetime` has no default: a stream message for an event that carries no `timestamp` makes `TradeUpdate(**data)` raise a pydantic `ValidationError` inside `TradingStream._cast`; the surrounding loop's generic `except Exception` logs it (`log.exception`) and continues with the same connection, so that update is lost to the handler. Docs list `timestamp` only for fill/partial_fill/canceled/expired/replaced/rejected; the alpaca-py test builds every event with a timestamp. Whether Alpaca sends `timestamp` on `new`, `accepted`, `pending_*`, `done_for_day` is not documented. [M: derived from code reading, behaviour not observed] — [alpaca/trading/stream.py L129-L154, L238-L320](https://github.com/alpacahq/alpaca-py/blob/dc5f6f53963b9e0e9e62bc35c9041a122aa95cdc/alpaca/trading/stream.py#L129-L154), [tests/trading/test_trading_models.py L387-L407](https://github.com/alpacahq/alpaca-py/blob/dc5f6f53963b9e0e9e62bc35c9041a122aa95cdc/tests/trading/test_trading_models.py#L387-L407)
- `TradingStream(raw_data=True)` skips model parsing and passes the raw `{"stream": ..., "data": ...}` dict to the handler. [H] — [alpaca/trading/stream.py L140-L154](https://github.com/alpacahq/alpaca-py/blob/dc5f6f53963b9e0e9e62bc35c9041a122aa95cdc/alpaca/trading/stream.py#L140-L154)

### Inferences
- For a reconciliation ledger keyed on fills, the natural dedupe key is `(order.id, execution_id)`, falling back to `(order.id, timestamp, qty, price)` when `execution_id` is null; the docs do not define `execution_id` uniqueness, so this is a design choice, not a documented guarantee. [L]
- Using `raw_data=True` and parsing with `Decimal` avoids float rounding in `price`/`qty` and avoids losing events to a missing-`timestamp` validation error, at the cost of writing the parser (the Order sub-object also needs tolerant parsing). [M]
- Handle `event` as a string (`str(getattr(e, "value", e))`) so that `done_for_day`, `order_replace_rejected`, `order_cancel_rejected` and `stopped` are not mistaken for unknown errors. A rejected cancel (`order_cancel_rejected`) is the stream signal behind spec step "anulowanie stopu odrzucone, bo stop już się wypełnił". [M]

### Gaps
- Which events carry `timestamp`/`execution_id`, ordering of `fill` vs order-status events, and duplicate/replay behaviour on reconnect: not documented. Paper test (single OTO or plain market order, raw capture): subscribe with `raw_data=True`, place one 1-share market order and one non-marketable limit that you cancel, log every raw frame, and list per `event` which keys are present.
- Whether `event_id` or `at` appear on single-leg equity events (they appear in the mleg example only).
